## Rationale
P3400, "Controlling Contract-Assertion Properties": the label framework --
`pre<L>(...)` -- and the machinery that turns a label into answers about
the contract it is attached to.  The separable facets follow in their own
commits; this is what they all need.

The design is that a label is **an ordinary C++ object**, not a syntax.
`pre<my_label>(...)` names something whose type answers questions by having
members, and the compiler asks those questions by constant-evaluating calls
on it.  That is why the framework is as large as it is:
`evaluateFacetConstant`, `facetCallViable`, `callLabelMethod` and
`applyLabelFacets` are a small overload-resolution-and-constant-evaluation
engine, run at compile time against a user-written type.

Three things worth a reviewer's attention:

**`warnNearMissFacet` exists because the failure mode is silence.**  A
label that *almost* provides a facet -- right name, wrong signature or
wrong constness -- simply does not provide it, and the contract gets the
default.  Nothing is ill-formed and nothing is diagnosed, so a typo in a
label's member costs you the behaviour you asked for with no indication.
The near-miss warning is the compensation, and
`dropInaccessibleFacetCandidates` is what keeps it from firing on members
that are private for good reason.

**`contract_control` is a keyword, and the reason is the using-directive.**
`using contract_control namespace N;` makes `N`'s labels findable from
contracts without making them findable from ordinary code, which needs its
own lookup list on `Scope` (that storage is in
`1070-p2900-base-sema-predicate-scope`) and its own parse path here.  It is
a `KEYWORD(contract_control, KEYCONTRACTSP3400)` entry in `TokenKinds.def`,
gated on the flag like the other per-paper keywords.

**Most of `<contracts>`'s growth is label algebra.**  The 439 added lines
here are `empty_label`, `review`, `fixed_message_label`, and above all
`operator|` -- combining two labels into one that answers each question
from whichever operand answers it.  That is library, not compiler, and it
is where a reader should start: the combination rules make the compiler
side much easier to follow.  `evaluation_semantic_set` removes one
semantic with `erase`, the name [support.contract.control.semset.mod]
gives it, as `std::set` does (`p3400-semantic-set-erase.cpp`), and
`is_continuing` lists the continuing semantics rather than negating
`is_terminating`, since a semantic can be neither: `assume` is,
continuing after a violation under it being undefined behaviour.

**A computed-semantics label is one whose result converts implicitly.**
[basic.contract.control] makes a type a computed-semantics control type
only if `t.compute_semantic(s)` is implicitly convertible to
`evaluation_semantic`, and the library concept says `convertible_to`.  So
the concept tests `__is_convertible`, the combined label assigns each
operand's result, and `callLabelMethod` converts the call implicitly
before constant-evaluating it: a facet returning `int`, another
enumeration or a class with only an `explicit` conversion does not
participate, statically or on the P3595 dynamic path, and a class with an
implicit conversion is applied through it
(`p3400-compute-semantic-convertible.cpp`).

`populateContractSemanticState` is where the whole thing lands -- the
resolved answers are written into the `ContractStmt`'s cached state, the
same slots `2400-p3595` fills from configuration.  Where both apply, that
is the interaction to look at.

## Compile gap
Needs `1020-p2900-base-ast` for the label slot on `ContractStmt`,
`1040-p2900-base-parse` for the cached `<...>` tokens -- that commit caches
them without parsing them precisely so this one can -- `1060-p2900-base-sema-core`,
`1070-p2900-base-sema-predicate-scope` for the contract-control lookup
storage, and `2400-p3595` for the semantic state it writes into.  All
precede it.

**Inward, six later commits reach into `applyLabelFacets`**: each facet in
`4230`-`4280` adds its question to the set this framework asks.  They are
not stubbed here -- the framework asks only about the facets it knows, and
each later commit adds one.

**Behaviour trap:** a label naming a facet this commit does not yet
implement is not an error.  It is a label whose facet is never consulted,
exactly like the near-miss case above, and with the same absence of a
diagnostic.  Between here and `4280-p3400-facet-queryable`, each
unimplemented facet behaves that way -- which is the expected intermediate
state, but is worth knowing before reading a test that "passes" at the
wrong commit.
