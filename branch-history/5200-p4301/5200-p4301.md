## Rationale
P4301, "Context Reports for the Contract-Violation Handler":
`contract_violation::report()`, a human-readable description of *why* the
violation was detected, supplied by whatever produced it.

**Eight lines of compiler source, and the reason is the ABI.**  The report
is an extensible field (`CXA_FIELD_REPORT`) populated lazily by the
producer, so the mechanism is entirely `2200-libcontracts`'s chain-walking
lookup, and the accessor is declared with the rest of
`contract_violation`'s interface.  What P4301 contributes is the flag and
`__cpp_lib_contracts_report` -- the same shape as `3600-p3099`, and for the
same 3.5(a) reason.

The producers are the sanitizers, which come later: ASan, UBSan and TSan
under `6030`-`6050`, plus MSan at `6060`, which GCC has no counterpart for.
Until those land, `report()` is correct and always answers the null case.

The one behaviour worth knowing is in the noexcept fallback.  `report()` is
`noexcept`, and a producer's populator is not required to be -- so an
escaping exception is caught and the report becomes "Error generating
report".  No shipping producer throws, which is exactly why
`p4301-report-noexcept-fallback.cpp` builds a throwing populator by hand:
without it the path has no coverage at all.

## Compile gap
Needs `1160-p2900-base-libcxx` for the accessor and `2200-libcontracts` for
the field lookup; both precede it.

**The producers come after.**  `6030-p3100-ubsan-runtime` and its siblings
are what make `report()` return anything, so between here and there every
test that exercises a populated report would have to construct one by hand
-- which is what the two `Runnable` tests here do.

**Behaviour trap:** a producer that populates the field without this
commit's gate is not an error; the field is simply never read.  And with
the gate on but no producer, `report()` answers null for every violation,
which is a correct answer and an easy one to mistake for a broken one.
