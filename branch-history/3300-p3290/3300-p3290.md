## Rationale
P3290, "Integrating Existing Assertions" -- **approved by EWG**.  A failing
`assert` reports through the contract-violation handler instead of calling
`abort` directly, and the library gains an API for reporting a violation
from code that is not a contract at all.

Almost all of it is library.  The compiler's share is the flag and the
`__clang_contracts_p3290` predefine that tells the library the facility is
available; the behaviour is in
`libcxx/include/__cassert/assert_contract.h`, which redefines `assert` to
call `__cxa_handle_cassert_violation` -- a violation with
`assertion_kind = cassert` and `detection_mode = predicate_false`, which
terminates on *any* completion of the handler, a normal return included.

Three things worth a reviewer's attention:

**The opt-in is three conditions deep and each one is load-bearing.**  The
integration applies only in C++26 or later, only when
`__clang_contracts_p3290` is predefined, and only when the program defines
`__STDC_WANT_ASSERT_USES_CONTRACTS__`.  Without the third, `assert` is
unchanged -- redefining it silently would change the behaviour of every
existing program that includes `<cassert>`.  The *capability* macro
`__cpp_lib_assert_can_use_contracts` is defined without the third
condition, because the question it answers is "could I ask for this",
not "did I".

**`assert_contract.h` has no include guard, on purpose.**  `<cassert>` is
required to redefine `assert` according to the current `NDEBUG` on every
textual inclusion, so a guard would make the second inclusion a no-op and
break that requirement.  `1160-p2900-base-libcxx`'s `assert.h` is the other
includer, and both include the C library's `<assert.h>` first so the
contract definition is the one that wins.

**The `view_interface` change is a real interaction, not a drive-by.**
Its hardening assertions call `empty()` on a `const` object; with the
assertion routed through a contract the call is constified, so it no longer
resolves to the non-const `empty()` some views provide.  `__is_empty_()`
casts the constness away for the call, preserving what the assertion meant
before.  It is the clearest small example of hardening and contracts
interacting, and there is a parked work item on the wider question.

`<assert.h>`'s own registration as a libc++ header is
`1160-p2900-base-libcxx`'s, because a header nothing registers is a header
the suite does not test.

## Compile gap
Needs `1160-p2900-base-libcxx` for `<contracts>` and the violation type,
and `2200-libcontracts` for the runtime that receives the report; both
precede it.

`__cxa_handle_cassert_violation` is declared by the header and **defined in
`libcontracts`**, which this commit does not touch -- the entry point is
already in `2200-libcontracts`'s version script by glob, so nothing is
owed there.

**Behaviour trap:** every guard above means that omitting this commit
leaves `assert` behaving exactly as it always has.  Nothing fails; the
integration is simply absent, and `__cpp_lib_assert_can_use_contracts` is
undefined.  That is why nine of this commit's tests are feature-test-macro
tests -- for a facility whose whole point is to be detectable and opt-in,
the macros *are* the interface.
