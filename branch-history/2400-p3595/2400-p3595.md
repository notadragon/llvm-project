## Rationale
P3595: choosing a contract's evaluation semantic from outside the source,
by command-line option, by inline JSON, or from a configuration file.

This is **not a standards proposal** -- there is no `-fcontracts-p3595`
flag and no feature-test macro, because there is nothing for a program to
detect.  It is a compiler facility, which is why its band sits below 3000
with the other compiler-only work rather than among the papers.

It is also the largest thing before the paper bands, and the reason is
`ContractOptions.cpp`: a JSON parser, an ordered rule list, and a matcher
that has to answer "which semantic applies to *this* contract" from a rule
that may constrain the contract's kind, its group, its enclosing namespace,
its source location and line range, whether the evaluation is caller- or
callee-side, and whether it is happening during constant evaluation.
First match wins, in command-line order.

Group matching is by dotted prefix: an entry's group selects every group
whose name is its own followed by a dot, so `ub:expr.mul` selects
`ub:expr.mul.div.by.zero.int.div`.  A small table of combined groups in
`groupMatches` names the groups that select leaves outside their own
name -- one, `ub:conv.lval.valid.representation.bool.enum`, the name the
P3100 invalid-value check reported before its `.bool` and `.enum` leaves.

Four things worth a reviewer's attention:

**`ContractConfig.h` is deliberately not `ContractOptions.h`.**  The latter
is pulled in transitively by `LangOptions.h` and therefore by most of
Clang, while `ContractConfigEntry` grows every time a new match criterion
is added.  Only the two translation units that build and resolve the
configuration include the new header; `ContractOptions` holds the data
behind a pointer.  The file's own comment says so, and it is the reason
adding a criterion later costs one rebuild rather than a full one.

**The per-statement attributes are the same facility from the other
direction.**  `[[clang::contract_group]]` and `[[clang::contract_message]]`
let a single contract say what the configuration or the source would
otherwise say about it, and `CheckForDuplicateContractAttrs` rejects either
one given twice.  Everything the base facility does with them is here too,
as declared cuts of the base functions it sits in: the group joins the
configuration query (`getConfigGroups`), and the message is a
message -- for `getUserMessage`, for the violation object, for comparing
two declarations' contracts, and for the error when a syntactic message is
given as well.

**Semantic resolution is cached on the `ContractStmt`, and the slots for it
are in the base AST.**  `1020-p2900-base-ast` defines
`CachedRuntimeSemantic_`, `CachedCESemantic_`, `CachedCallerSemantic_` and
the `Dyn*` fields; this is the commit that fills them.  Until now
`ensureRuntimeSemantic` answered with the kind's default for everything.

**Dynamic selection reaches into CodeGen.**  A rule whose output is a
`dynamic` descriptor makes Sema precompute a per-return-value transform
table, and `CGContracts.cpp` emits a dispatch switch over it -- so the
semantic is chosen at link or run time rather than at compile time.  The
`CGContracts.cpp` hunks here are that switch and the selector's symbol: a
"C++"-linkage selector name is looked up as a qualified name (following
inline namespaces) and a declared selector is called by its own mangled
name; only an undeclared one is mangled from the configured string.  So the
configuration parser accepts as a selector name only identifiers separated
by `::` ("C++") or a single identifier ("C"): anything else would reach
the object file as an invalid or ambiguous symbol.  The lookup is
`ContractStmt::lookupDynamicSelector` (`StmtCXX.cpp`), because Sema uses it
too: at the end of the translation unit it finds each declaration with a
selector's name but not its type (`int ns::sel ()`, or a variable) and
warns at it under `-Wcontract-configuration`, since such a function's
result would otherwise be read as a semantic.

A dynamic selection never brings in a throwing semantic (observe or
enforce, whose violation handler may let an exception leave the check)
that the contract's allowed set does not hold (`contractSemanticsNothrow`,
DECISIONS.md E137 and E138): under a label allowing neither, a
`compute_semantic` result outside the set is an invalid selection, as the
static path rejects it (`precomputeDynamicTable`), and an invalid selection
is reported through the noexcept_enforce entry point instead of the enforce
one with `-fcontracts-p4298`, and as a quick_enforce trap without it,
whatever the label allows (in the dispatch, which sits with
`1100-p2900-base-codegen`'s `EmitContractStmtAsFullStmt`).  The tests,
which need P3400's labels and P4298's semantics, are in `4800-p4298`.

A selector's weak default (`provideweak`) returns the matched entry's
configured semantic as written (`ContractDynamicResult::Configured`, kept
on the `ContractStmt` with the descriptor), not the contract's compile-time
semantic: the dispatch adjusts whatever the selector returns to the allowed
set and passes it through the label's `compute_semantic`, so returning the
already-adjusted semantic would apply both twice, and a `compute_semantic`
need not be idempotent.  It is also the only value that serves every
contract sharing the symbol, the weak definition being one per symbol and
the label per contract; it is not adjusted to the flags either, so every
translation unit, C or C++, emits the same definition.  Two entries naming
one selector with different semantics get the first contract's.

91 of this entry's 105 files are tests, which is the right ratio for a
feature whose whole surface is "given this configuration and this
contract, what happens".

## Compile gap
Needs `1000-p2900-base-basic` for the semantic enumeration,
`1020-p2900-base-ast` for the cache slots, `1060-p2900-base-sema-core` for
the contract-specifier to resolve against, and `1100-p2900-base-codegen`
for the emission path the dynamic switch extends.  All precede it.

None outward: nothing later calls into the configuration machinery, and the
later papers that participate in matching -- P3400's labels most of all --
extend `ContractConfigEntry` from their own commits.

**One backward reference:** the `CompilerInvocation.cpp` pieces (the
umbrella's implications, the P4298 and P4405 flags' availability and
warnings, and `-fcontracts-p4405`'s implication of the proving-strategy
flags) name the per-paper options `OPT_fcontracts_p3097` through
`OPT_fcontracts_p4405` and `OPT_fcontracts_prove_fold`/`_assume`, each
declared by its own paper's commit (the last two by `4910-p4405-fold`).  Standing
alone this needs those options stubbed in `Options.td`, as
`1140-p2900-base-driver` does; each paper's commit replaces its stub.

**Behaviour trap:** the rules this commit adds are additive and default to
"no rule matches", so omitting it changes no program's behaviour except
that `-fcontract-evaluation-semantic=` and its three siblings are not
recognized.  The failure is a rejected command line, not a silently
different semantic -- which is the right way round, and worth saying
because the reverse would be very hard to notice.
