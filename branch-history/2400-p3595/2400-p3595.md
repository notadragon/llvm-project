## Rationale
P3595: choosing a contract's evaluation semantic from outside the source,
by command-line option, by inline JSON, or from a configuration file.

This is **not a standards proposal** -- there is no `-fcontracts-p3595`
flag and no feature-test macro, because there is nothing for a program to
detect.  It is a compiler facility, which is why its band sits below 3000
with the other compiler-only work rather than among the papers.

It is also the largest thing before the paper bands, and the reason is
`ContractOptions.cpp`: a JSON parser, an ordered rule list, and a matcher
that has to answer "which semantic applies to *this* contract" from a rule
that may constrain the contract's kind, its group, its enclosing namespace,
its source location and line range, whether the evaluation is caller- or
callee-side, and whether it is happening during constant evaluation.
First match wins, in command-line order.

Four things worth a reviewer's attention:

**`ContractConfig.h` is deliberately not `ContractOptions.h`.**  The latter
is pulled in transitively by `LangOptions.h` and therefore by most of
Clang, while `ContractConfigEntry` grows every time a new match criterion
is added.  Only the two translation units that build and resolve the
configuration include the new header; `ContractOptions` holds the data
behind a pointer.  The file's own comment says so, and it is the reason
adding a criterion later costs one rebuild rather than a full one.

**The per-statement attributes are the same facility from the other
direction.**  `[[clang::contract_group]]`, `contract_semantic`,
`contract_emission` and `contract_message` let a single contract say what
the configuration would otherwise say about it, and
`CheckForDuplicateAndIncompatibleContractAttrs` is the one place that
decides which combinations are contradictory.

**Semantic resolution is cached on the `ContractStmt`, and the slots for it
are in the base AST.**  `1020-p2900-base-ast` defines
`CachedRuntimeSemantic_`, `CachedCESemantic_`, `CachedCallerSemantic_` and
the `Dyn*` fields; this is the commit that fills them.  Until now
`ensureRuntimeSemantic` answered with the kind's default for everything.

**Dynamic selection reaches into CodeGen.**  A rule whose output is a
`dynamic` descriptor makes Sema precompute a per-return-value transform
table, and `CGContracts.cpp` emits a dispatch switch over it -- so the
semantic is chosen at link or run time rather than at compile time.  The
two `CGContracts.cpp` hunks here are that switch.

91 of this entry's 105 files are tests, which is the right ratio for a
feature whose whole surface is "given this configuration and this
contract, what happens".

## Compile gap
Needs `1000-p2900-base-basic` for the semantic enumeration,
`1020-p2900-base-ast` for the cache slots, `1060-p2900-base-sema-core` for
the contract-specifier to resolve against, and `1100-p2900-base-codegen`
for the emission path the dynamic switch extends.  All precede it.

None outward: nothing later calls into the configuration machinery, and the
later papers that participate in matching -- P3400's labels most of all --
extend `ContractConfigEntry` from their own commits.

**Behaviour trap:** the rules this commit adds are additive and default to
"no rule matches", so omitting it changes no program's behaviour except
that `-fcontract-evaluation-semantic=` and its three siblings are not
recognized.  The failure is a rejected command line, not a silently
different semantic -- which is the right way round, and worth saying
because the reverse would be very hard to notice.
