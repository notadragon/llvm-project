## Rationale
P3098, "Contract Postcondition Captures": `post [c = x] (...)`, so a
postcondition can compare against a value taken *before* the body ran.

The feature is two-phase by construction and that is what most of the code
is about.  A capture's initializer is evaluated in the function prologue,
alongside the precondition checks; the predicate that reads it runs in the
epilogue.  Between those two points the body can do anything, including
throw, so the capture's storage has to outlive its own block scope and its
construction has to be guarded.

Two things worth a reviewer's attention:

**A capture whose construction throws is a `post_capture` violation, and
the guard is unconditional on purpose.**  `EmitPostconditionCaptureInit`
always wraps the construction in a catch-all, where the predicate path
skips the try/catch when Sema found the predicate cannot throw
(`ContractStmt::predicateCanThrow`).  Nothing records the same answer for a
capture's construction, and an unguarded exception would propagate out of
the prologue.

**`observe` must skip the predicate, not fall through to it.**  When
construction fails under `observe` the violation is reported and execution
continues, but the capture does not exist; evaluating the predicate would
read it.  `CaptureInitFailed` is the per-capture flag that records this, and
`LoadPostconditionCaptureFailed` is what the epilogue checks.  There is no
re-check to fall back on here, unlike the predicate-throw path, because
construction either happened or did not.

**Constant evaluation is here too.**  `EvaluatePostconditionCaptures` binds
each capture in the constant-evaluation call frame at entry, with
`ScopeKind::Call` so the value survives the body's own block scopes
closing -- the mirror of what the codegen prologue does.  It lives inside
`HandleFunctionCall`, between the base facility's precondition call and its
return, so this commit claims those lines as declared cuts of the two
segments rather than the whole function.  `HandleConstructorCall` and
`HandleDestructionImpl` run the same steps -- preconditions, captures, and
postconditions around the body (a destructor's once the object is destroyed,
as at run time) -- and are claimed here whole because the capture scope is
threaded through them; before this, the constant evaluator checked no
contract of a constexpr constructor or destructor.  The same steps run for
a P3097 virtual call's statically named function around its final
overrider's call (the `Interface` frame in `VisitCallExpr`), in the order
the call-site wrapper uses at run time; that needs both P3097 and the
capture scope, so it is here rather than in `3000-p3097`.

**A capture's initializer is in the contract assertion; the capture is
not.**  So an entity declared outside the assertion -- `this` included -- is
constified in the initializer as in the predicate (the captures are parsed
in a contract scope), while an init-capture is deduced as `auto` would be,
without the initializer's top-level cv, and a lambda in the predicate that
copies a capture gets a member it may modify when mutable.

**Two pieces of P3098 are not in this commit**, and a reviewer looking for
them should know where they went: the `PostconditionCapture` decl node is
in `1020-p2900-base-ast` with the rest of the AST, and the parser's token
handling for the capture list is in `1040-p2900-base-parse`.  Both are
slots that this commit fills, consistent with how those commits treat every
other paper.

A P3595 dynamic selector is an ordinary function, so an exception from it
unwinds through the evaluating function's handlers and cleanups: both the
dispatch's call (`1100-p2900-base-codegen`) and the one a postcondition
with captures makes where the captures are initialized
(`EmitDynamicEffectiveSelection`) are calls or invokes as the EH scope
asks.  The test, `Runnable/p3595-dynamic-selector-throws.cpp`, exercises
both, so it is here.

## Compile gap
Needs `1020-p2900-base-ast` for the capture node and the `HasCaptures`
slot, `1040-p2900-base-parse` for the token handling, `1060-p2900-base-sema-core`
for the contract-specifier to attach captures to, `1100-p2900-base-codegen`
for the emission path, and `2400-p3595` for the semantic resolution the
capture path branches on.  All precede it.

None outward.

**Behaviour trap:** with the flag off, the capture syntax is diagnosed at
parse time, so the failure is loud.  The quiet failure is the other one --
capture *construction* order.  A capture initialized in the epilogue rather
than the prologue would read post-body state and every ordinary test would
still pass, because the values usually agree.  The tests that would catch
it are the ones that deliberately mutate the captured object in the body,
and they are the reason this entry has forty files.
