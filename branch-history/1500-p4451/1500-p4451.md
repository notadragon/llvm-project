## Rationale
P4451R2, "Early Adoption of an Always-Enforced Label": an
assertion-control-specifier `< id-expression >` naming
`std::contracts::controls::enforced` after `pre`, `post` or
`contract_assert` makes a contract assertion a terminating one, every
evaluation of which uses a terminating semantic.  `-fcontracts-p4451`
enables it, and P4451R2 being part of C++26, `-std=c++26` and every later
standard imply it when contracts are on (`ParseLangArgs`; only the
language mode, not `-fcontracts` with an earlier standard), unless
`-fno-contracts-p4451` is given, which `GenerateLangArgs` records.  It stands on the C++26 facility alone, and comes directly
after it, before every other paper.

The specifier's id-expression is checked but never built as an expression:
the assertion gets a bit, `IsTerminating`, and the allowed semantics of a
terminating assertion -- `TerminatingContractSemanticsMask`, enforce and
quick_enforce -- set in `BuildContractStmt` before the semantic is
resolved.  The base facility already resolves every contract's semantic
through its allowed set (`ContractQuery::AllowedMask`), so a semantic
outside it, ignore or observe, is adjusted to enforce, at run time and in
constant evaluation alike, and quick_enforce is kept.  There is no label
object, so the violation record is an unlabelled assertion's and nothing
in the ABI changes.  The bit survives template instantiation
(`TreeTransform`), serialization, `ASTImporter`, and takes part in
profiling, ODR hashing and redeclaration matching (both declarations'
assertions have the specifier or neither does).

**The check runs where the specifier is parsed.**
[basic.contract.control] requires the id-expression not to be dependent
and name lookup for it to find the standard library declaration of
`std::contracts::controls::enforced`.  `ParseContractLabelAndRequiresClause`
takes the specifier's tokens, and `splitTerminatingSpecifier` reduces them
to the only id-expression form that can name a namespace-scope variable,
an optional `::` and identifiers joined by `::`;
`CheckTerminatingSpecifier` then looks the name up as the language does --
each qualifier as a nested-name-specifier, so only a namespace or
namespace alias leads on and a dependent type is a dependent name, the
last name by ordinary lookup, unqualified from the specifier's scope or
qualified in the namespace -- and compares what it finds with the
declaration qualified lookup from `std` finds, the inline-namespace one
libc++ declares.  Lookup finds only what is visible, including what an
imported module exports.  For a member function the check is the late
parse at class completion, with the parameters re-entered, as for the
predicate, so a later member is found.  Anything that fails is one error,
`err_contract_terminating_specifier`, saying why; nothing in the specifier
is also reported as an undeclared name.  The late-parse cache keeps every
specifier under P4451; without it, one naming `enforced` is pointed at
the option (`isTerminatingSpecifier`).

**The library follows the option.**  `__cpp_contracts` and
`__cpp_lib_contracts` take P4451R2's value, 202611L, and
`__clang_contracts_p4451` is defined; under it `<contracts>` and the std
module declare `std::contracts::controls::enforced` alone, of an internal
type in an inline namespace.  The feature-test-macro generator gains a
`raised` field for a macro an unadopted extension raises under a compiler
macro.

The tests run under `-fcontracts-p4451`: each spelling the lookup rule
accepts and each it rejects, in templates too (each ill-formed specifier
diagnosed once, a dependent one at the definition); lookup that a later
member, a parameter or a using-directive changes; a specifier before
`<contracts>`; redeclarations; the diagnostics on every kind of assertion
and with the option off; the feature-test macros; the language modes that
imply the option (`p4451-cxx26.cpp`); the label with libstdc++
(`p4451-libstdcxx.cpp`); and in modules `import
std;`, `import std.compat;`, `import <contracts>;`, an implementation unit
and a global module fragment, which does not make the declaration visible
to an importer.  Where a test also runs under `-fcontracts-p3400`, those
RUN lines are `4285-p4451-under-p3400`'s.

## Compile gap
None of its own: what it uses is the base facility's -- the allowed set on
`ContractStmt` and in `ContractQuery`, the late-parse cache, `<contracts>`
-- and all of it precedes it.

**What threads through shared code lands with that code's owner**, as for
every paper in this history: the `ContractStmt` bit and its accessors,
serialization, import, profiling and dumping (`1020`, `1120`), the
parser's and Sema's `IsTerminating` parameters, the late-parse cache's
keep-or-diagnose and the specifier's parse (`1040`, `1060`), the
redeclaration comparison (`1060`), the option's sub-flag entry (`1140`),
and libc++'s `<version>` value, its generator and the std module's export
(`1160`).  Each reads `ContractsP4451` or the bit, which nothing sets
before this commit.

Later papers add to it rather than replace it: `2400-p3595` defines the
resolution through the allowed set (configured, inline-JSON and dynamically
selected semantics), `4930-p4405-analysis` adds prove to
`TerminatingContractSemanticsMask`, `4200-p3400-core` makes the specifier
step aside under `-fcontracts-p3400` (whose label it then is: the step-aside
is in the base facility's parse, inert until `ContractsP3400` is set) and
has `-fcontracts-p3400` imply `-fcontracts-p4451`, as
`2900-umbrella-option` has `-fcontracts-p3850`; `6900-cross-paper-options`
forwards the option from the driver with every other per-paper option and
adds the option rule, and with it `-fcontracts-p4451` enabling contracts
before C++26.
