## Rationale
P4405, "prove and diagnose evaluation semantics": the two semantics exist
everywhere a semantic can be named, and an evaluation with `prove` is an
error, one with `diagnose` a warning, "contract assertion cannot be proven",
unless a proving strategy proves its predicate.  This commit adds the
strategy interface and its dispatcher but no strategy, so every evaluation
is diagnosed; `4910-p4405-fold` adds the first.  Neither semantic has any
run-time effect: the predicate is never evaluated, as for `ignore`.
`-fcontracts-p4405` (implied by `-fcontracts-p3850`) admits `prove` (8) and
`diagnose` (9) -- the next free values after `noexcept_enforce`, not the
paper's 5 and 6 -- to every contract's allowed set and predefines
`__cpp_contracts_prove`.  The diagnose warning is the new
`-Wcontract-unproven`, on by default.

The two semantics form a new category: active, but with no run-time check.
A contract with `ignore` or `assume` emits nothing; one with `prove` or
`diagnose` reaches the point where its check would be emitted,
`emitCheckForSemantic`, which emits nothing and calls
`diagnoseUnprovenContract` instead.  That describes the evaluation in a
`ContractProofQuery` and makes the one call `proveContract`
(`CodeGen/ContractProve.h`): it asks each enabled strategy in the registry
(`ContractProve.cpp`, null-terminated), each defined in a file of its own
behind `ContractProofStrategy`, and the evaluation is diagnosed when none
proves it -- "contract predicate is always false" when one shows the
predicate false.  A proof is sound, or conditional when it relies on an
earlier assertion that is not guaranteed to hold (a strategy records
whether it may depend on such assumptions); both suppress the diagnostic.
So a callee-side evaluation is
diagnosed in the function body: only for code that is emitted, once per
template instantiation, and never under `-fsyntax-only`
(`p4405-template.cpp`, `p4405-syntax-only.cpp`).  An evaluation is
diagnosed once even when its code is emitted twice (a constructor's
complete and base variants, `p4405-prove.cpp`).  A caller-side evaluation
is diagnosed at the call, by `DiagnoseCallerSideProvingContracts` from
`EmitCallExpr` and `EmitCXXConstructExpr`, with a note at the predicate
(`p4405-caller-side*.cpp`) -- for a precondition the query carries the
callee, so that a strategy may use the call's arguments; a call of an
inheriting constructor evaluates the inherited constructor's contracts.
Clang implements no other caller-side checking, and needs none for these.  The error for `prove` is recoverable
(`DiagnosticIDs::isUnrecoverable`): code generation, which stops at the
first unrecoverable error, must go on to diagnose every other evaluation.

Most of the compiler-side change teaches existing machinery about the new
category, and those lines sit with the commits that wrote it: the
enumerators, names, masks and `isProvingContractSemantic` with
`1000-p2900-base-basic`; the allowed-semantics mask, moved out of
`ContractStmtBits` into a `uint16_t` member wide enough for bits 8 and 9,
with `1020-p2900-base-ast` and `1120-p2900-base-serialization`; the best
fit (`clampToAllowed`, `4230-p3400-facet-allowed-semantics`), which puts
both at `ignore`'s level, where `ignore` is preferred, then `diagnose`,
then `prove` -- a `prove` that is not allowed becomes `diagnose`, failing
that `ignore`, a `diagnose` becomes `ignore`, failing that `prove`, and any
other semantic whose walk reaches the level with `ignore` not allowed
becomes `diagnose`, failing that `prove`, so a label allowing only `prove`
(D4405's `always_prove`) works whatever the build configures
(`p4405-labels*.cpp`) -- and which now answers "no valid semantic", for an
empty allowed set, rather than passing a candidate through outside it,
with a `static_assert` that every semantic has a level;
constant evaluation skipping them as `ignore` with `1090` (and the
capture binding with `4000-p3098`); the P3595 table recording them as
`ignore`, the `compute_semantic` range check and the "no valid evaluation
semantic" error with `2400-p3595` and `4200-p3400-core`; the P3097
wrappers, which are not built for them, with `3000-p3097`; and the P3100
assertion that no implicit allowed set holds them with `6000-p3100-core`.
The flag's warnings live where P4298's do: the command-line one in
`CompilerInvocation.cpp`'s `ParseLangArgs` piece and the configuration one
in `initConfig`, both `2400-p3595`'s, as are the diagnostic definitions in
`DiagnosticCommonKinds.td`.  What this commit itself holds is what is
P4405's alone: the flag and macro, `diagnoseUnprovenContract` and its two
call paths, the proving interface and dispatcher, the recoverable error,
and the tests.  The proving-strategy flags follow the same split:
`LangOptions.def` with `1000-p2900-base-basic`, the implication by
`-fcontracts-p4405` in `CompilerInvocation.cpp` and the "always false"
diagnostics with `2400-p3595`, the forwarding with
`6900-cross-paper-options`; the options and the strategy are
`4910-p4405-fold`'s.

A diagnostic of an evaluation in a template instantiation is followed by
the notes Sema gives a diagnostic there ("in instantiation of ... requested
here" for each level, `-ftemplate-backtrace-limit` honoured), although code
generation issues it after Sema's instantiation stack is gone.  Under
`-fcontracts-p4405`, Sema records the notes `PrintInstantiationStack` would
print when it instantiates a function definition
(`InstantiateFunctionDefinition`) or a lambda's body
(`TemplateInstantiator::TransformLambdaBody`, which adds Sema's "while
substituting into a lambda expression"), in a table the `ASTContext` holds
(`setContractInstantiationNotes`, by canonical declaration, a handle per
entry).  Code generation looks up the function it is emitting
(`getContractDiagnosticContext`; a lambda's call operator or a block not
recorded itself takes its enclosing function's), which renders the notes'
text while the AST exists, and follows the diagnostic with them
(`emitContractDiagnosticContext`, as `note_contract_instantiation_context`,
defined with the other P4405 diagnostics in `2400-p3595`'s lines), before
the note at the predicate of a caller-side one, as Sema orders them: once
for consecutive diagnostics of one instantiation, as Sema prints its stack
once, none after a diagnostic that is not shown, and none for a
non-template function.  A caller-side evaluation takes its caller's
(`p4405-template-instantiation-context.cpp`).

The interface also describes D4405's override pairs
(`ContractOverridePair`), for `4940-p4405-override`: the query names the
pair an obligation belongs to and whether the pair's override shadow
decides it, and `diagnoseUnprovenContract` diagnoses such an obligation at
the overriding function's definition, naming the overridden function.

## Compile gap
**Behaviour gap: the driver does not pass `-fcontracts-p4405` on before
`6900-cross-paper-options`.**  As for every per-paper flag, the forwarding
in `Clang.cpp`'s `ConstructJob` is one block that lands there; until then
only a `-cc1` command line sees the flag.  This commit's tests that use the
driver (`Runnable/`, the `libcxx` one) cannot pass before `6900`, and
`p4405-p3100-unaffected.cpp` needs `6000-p3100-core`.
`p3400-is-continuing.cpp`, which checks `is_continuing` for every
semantic -- `assume` is neither terminating nor continuing, and
`unspecified` is continuing -- names the P4298 and P4405 enumerators, so
it lands here.

Nothing else is owed forward.  Every identifier the P4405 lines elsewhere
use is declared at or before their commit, with one exception in the other
direction, the same as P4298's: the `-fcontracts-p4405` lines in
`CompilerInvocation.cpp` (`2400-p3595`) and `wantsCxxContracts`
(`1140-p2900-base-driver`) name `OPT_fcontracts_p4405`, which this commit
declares; those commits' gaps cover it.  The C mode's tests
(`clang/test/Contracts/C/c-p4405-*.c`) ride with `5000-p4299`, the next
commit, as gnu_gcc's do.
