## Rationale
The first proving strategy for the P4405 `prove` and `diagnose` evaluation
semantics, folding, and the flags that select strategies.  An evaluation
with either semantic is diagnosed unless an enabled strategy proves its
predicate; with no strategy enabled every evaluation is diagnosed
("contract assertion cannot be proven"), as `4900-p4405` leaves it.

`-fcontracts-prove-fold` (implied by `-fcontracts-p4405`, so by the umbrella
`-fcontracts-p3850`; `-fno-contracts-prove-fold` turns it off on either side
of it) proves a predicate that the constant evaluator folds to `true` in its
folding mode -- not manifestly constant-evaluated, so
`__builtin_is_constant_evaluated()` is false as at run time -- whether or
not it is a constant expression: a `constexpr` call, `sizeof(T) >= 4` in an
instantiation, a constant local, `x > 0 || true`.  A predicate that folds to
`false` is diagnosed as "contract predicate is always false" instead (an
error for `prove`, a `-Wcontract-unproven` warning for `diagnose`).  Folding
assumes nothing but the language's rules, so its proofs are always sound.
It never evaluates the predicate at run time, and one whose value is known
but which may have side effects of its own (`touch() || true`) stays
unproven.  The constant evaluator knows nothing of a parameter's value, so
`x == x` is not folded (gnu_gcc's folder proves it).

For a caller-side evaluation of a precondition, the predicate is folded as
if in a call to the callee, so that `divide(n, 0)` against `pre(d != 0)` is
always false and `divide(n, 2)` proven.  Only a by-value parameter of scalar
type whose argument folds to a constant without side effects (or to the
address of a static object) holds its argument -- default arguments,
enumerators, `nullptr`, `&global`, the elements of a parameter pack and the
arguments of a member function, operator or constructor call included --
and `this` designates the object when that is a static one.  Every other
parameter (a reference, a class type, a non-constant argument; every
parameter of a lambda) is an unknown value, which keeps the proof sound.
`Expr::EvaluateAsBooleanConditionInCall` (`ExprConstant.cpp`) is the
evaluator's side: it builds the call frame with only those parameters
bound, as `EvaluateWithSubstitution` does for `enable_if`, but in folding
mode.

`-fcontracts-prove-assume` (implied the same way) is accepted; it asks for
a soundly proven evaluation to be treated as an assumption, which for a
predicate proven by folding adds nothing, so with folding the only
strategy it has no effect.

The strategy is `ContractProveFoldStrategy` in
`CodeGen/ContractProveFold.cpp`, the registry's one entry; it records that
it never depends on earlier assertions.

## Compile gap
None of its own.  The strategy uses only `4900-p4405`'s proving interface
(`ContractProve.h`).  As for `-fcontracts-p4405`, the lines that make
`-fcontracts-p4405` imply the two flags (`CompilerInvocation.cpp`,
`2400-p3595`) name `OPT_fcontracts_prove_fold` and
`OPT_fcontracts_prove_assume`, which this commit declares; that commit's
gap covers it.  The `LangOptions.def` entries are `1000-p2900-base-basic`'s.

**Behaviour gap: the driver does not pass the two flags on before
`6900-cross-paper-options`**, whose contracts block in `Clang.cpp`'s
`ConstructJob` forwards them, as for `-fcontracts-p4405` itself; until then
only a `-cc1` command line sees them.  The tests that use the driver (the
`DRIVER` lines, `Runnable/p4405-fold-*.cpp`) cannot pass before `6900`.  The
C mode's tests (`clang/test/Contracts/C/c-p4405-fold-*.c`) ride with
`5000-p4299`, as `4900-p4405`'s do.
